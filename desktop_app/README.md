# Ruby Agent Desktop

Ruby is a Windows Electron application with a bundled Python assistant runtime. In a release
install, Electron starts the backend, waits for its authenticated loopback bridge, and stops it
when Ruby closes. The user does not need Python, Node.js, Git, a repository checkout, or a
manually started bridge.

## First launch

Install Ruby and open it from the Start menu or desktop shortcut. On first launch, copy your
Gemini API key, then choose **Paste key and start Ruby**. Electron's main process reads the
clipboard directly, checks the key, stores it encrypted with Windows secure storage under the
current user's application data, and clears the clipboard if it still contains that key. The
React renderer never receives the key. Python receives it only in the backend process environment.
The bridge token is generated by Electron for each launch and passed directly to Python in its
environment. Both processes communicate over loopback.

The assistant workspace is `%LOCALAPPDATA%\Ruby\BackgroundWorkspace`. App configuration and
logs/runtime data use Electron's per-user `userData` directory. The bundled application files
are read-only install resources.

## Development

Install Node.js 22.12+ and Python 3.12+, then from the repository root install the desktop
backend dependencies:

```powershell
python -m pip install -r requirements-desktop.txt -r requirements-desktop-build.txt
cd desktop_app
npm ci
npm run desktop:dev
```

`desktop:dev` starts Vite and Electron. Electron starts the production Python launcher in
managed mode; it does not use `DemoPlanner` or require a separately started bridge. Ruby asks
for the Gemini key in the UI. To select a non-default Python executable during development,
set `RUBY_PYTHON_EXECUTABLE` before running `npm run desktop:dev`.

`npm run dev` remains a browser-only frontend preview. It does not start Python or connect to
the bridge.

## Build and installer

On Windows, with Python 3.12+, Node.js 22.12+, and network access for the initial dependency
download, run:

```powershell
python -m pip install -r requirements-desktop.txt -r requirements-desktop-build.txt
cd desktop_app
npm ci
npm run desktop:dist
```

The build creates an onedir PyInstaller runtime, includes it as an Electron resource, builds
the React assets, then produces the NSIS installer in `desktop_app/release/`. The GitHub
Actions Windows workflow runs this same packaging path. The installer must be tested on a
clean Windows machine before release; a successful local package build alone does not prove
first-run behavior on a machine without developer tools.

## Window and orb behavior

Ruby opens the full Control Center. Minimizing or closing it collapses to a small
always-on-top orb; clicking the orb restores the Control Center. Electron's main process
polls the loopback bridge and forwards task state, progress, and execution-mode changes to
both renderers. The orb follows that state: it thinks while managed tasks run, turns cyan
and tracks F16's pointer target during `cursor_control`, flashes green on completion, turns
red after an error or cancellation, then returns to idle. Orb clicks remain active during
a task.

## Runtime boundary

The production path is Electron → authenticated loopback bridge → task router. `task_doing`
and `background_task` use the managed `GeminiPlanner` / filesystem action pipeline.
`cursor_control` explicitly delegates to the existing F16 autonomous agent and is the only
mode that controls the real desktop. Destructive file actions and overwrites require
approval. Process/shell, browser, and GUI actions remain disabled inside the managed
pipeline. The legacy voice assistant is separate and is not started by this desktop app.

Run the deterministic checks from the repository root and desktop directory:

```powershell
python -m unittest discover -s tests -p "test_*.py" -v
python -m unittest discover -s tests/background_agent -p "test_bg_*.py" -v
cd desktop_app
npm run test:electron
npm run build
```

Electron uses context isolation, sandboxing, and a narrow preload API. The renderer can submit
the key it is currently collecting during setup, but it cannot retrieve the saved key or the
bridge token. API requests are made by Electron's main process.


## Conversational chat

The Control Center's **Chat** tab uses the authenticated local bridge endpoint `POST /v1/chat`, separate from `POST /v1/tasks`. Chat messages do not submit work to the task planner or desktop operator. Choose **New task** inside the Chat view when you want Ruby to execute work using an execution mode.

Conversation history is held in memory by the running Python process and is isolated by conversation ID. The latest ten turns are retained; starting a new conversation resets the UI to a fresh ID. History is not persisted across backend restarts.

Gemini chat model configuration is read from environment variables:
- `RUBY_GEMINI_MODEL` (or `GEMINI_MODEL`): primary model shared by chat and task planning. The older `RUBY_GEMINI_CHAT_MODEL` / `GEMINI_CHAT_MODEL` names are accepted as aliases.
- `RUBY_GEMINI_FALLBACK_MODELS`: comma-separated alternatives tried if a request fails.

Defaults are documented in `.env.example`. Availability depends on the models enabled for the configured Gemini API key.
